# Security operations and remaining activation

Application protections include authenticated membership, independent approvals, private retained evidence, immutable activity history, request guards/limits, security rejection records, SHA-256 integrity checks, scan-based quarantine and encrypted backup export. This is not a security certification or a promise that compromise cannot happen. Hosting dispatch remains the authentication boundary; do not expose the underlying Worker or widen the sole-owner audience while the shared monitor updater is enabled.

## Malware scanner activation
All evidence, including legacy files, requires a matching clean malware verdict before downloads, evidence linking, finding approval, issue, AI assistance or completion submission. Clean verdicts expire in seven days. Failed, infected, expired, mismatched and missing verdicts remain quarantined; there is no manual release bypass. File signatures alone do not establish malware safety. The scanner is currently **not connected**.

An adapter for a privately operated ClamAV service is included under scanner/. It now uses two synchronous Gunicorn workers, runs all container processes as the non-administrator clamav user, checks the loaded database date rather than file modification time, bounds engine response frames and deadlines, and exits if a required daemon stops. Twelve contract tests pass with an in-memory ClamD transport, covering exact streamed bytes, infected verdicts, incomplete/error replies, stale/future signatures, authentication, framing, altered bytes and readiness. This does not validate a live engine, HTTP ingress or the container build: Docker, ClamAV and local Unix-socket access were unavailable in this execution environment. It has not been deployed or validated against a live engine here. Build with a container provider under the owner's control, terminate TLS, maintain signature updates, isolate the service from other networks/data, impose ingress/concurrency limits, use a private secret (at least 32 characters), and test clean, EICAR, encrypted/archive-limit, failure and stale-signature cases. Do not send confidential documents to public scan-sharing services.

Set AUDIT_SCANNER_URL to that private service's HTTPS /scan URL and AUDIT_SCANNER_TOKEN as a server-side secret through Sites runtime settings, then publish to apply configuration. Scanner input is the exact file bytes with X-Evidence-SHA256 and bearer authentication. Response: verdict clean/infected, matching sha256, engine, version, signaturesUpdatedAt (less than seven days old). Worker requests time out after 45 seconds, reject redirects and fail closed. Rescan retained files from the owner-only Security centre. An engine verdict reduces risk but does not guarantee benign documents. See scanner/README.md for the operator deployment and acceptance procedure. The container is a prepared adapter, not an independently reviewed deployment.

## Backup export and recovery
The owner-only Security centre exports a complete bounded record/file snapshot and encrypts it in the browser with AES-256-GCM, random salt/nonce and PBKDF2-HMAC-SHA256 (600,000 iterations). The passphrase never reaches the server. Browser encryption/decryption is checked before offering the download. Keep the encrypted file outside the hosting account and its passphrase separately. Losing the passphrase prevents recovery. Quarantined bytes remain encoded inside the encrypted backup; do not execute or open them without scanning.

Exports refuse more than 2,000 rows per table, 8 MB structured records or 16 MB evidence rather than silently truncating. All stored evidence must exist and match its hash; registered but unconfirmed missing uploads are explicitly recorded as missing. Database metadata is read in a batch snapshot and object keys are immutable through the app. Secrets, hosting settings and source code are not included; retain the source/migrations and secret recovery process separately. Failed export attempts are recorded; a request or browser encryption check does not prove independent storage or recovery.

The automated tests decrypt a fixture and restore its rows/file bytes into an isolated test database. A live institutional restore drill, independently protected scheduled backups and provider object-lock/retention are still **not verified**. Large datasets require an operator-managed export/backup pipeline beyond these bounded exports.

## Identity, monitoring and independent assessment
Enable MFA and secure recovery on ChatGPT, GitHub and hosting/provider administrator accounts. This app cannot configure or verify those account settings. Review invitations and remove access by revoking members, preserving identity history.

The Worker limits API traffic per platform identity and request group (120 reads/min, 60 writes/min, 30 evidence downloads/min, 12 upload requests/min, two backup exports/min). Counters are shared in D1. This is an application abuse control, not a provider DDoS firewall. Security history records app-level rejected requests and workflow denials with actor identity where dispatch supplies it; pre-dispatch/anonymous traffic and provider events are outside this history. Request bodies, passphrases, credentials and query strings are not recorded. Raw unauthenticated failed callers are labelled as unidentified, not attributed to a human.

Review security events, patch dependencies, configure provider alerts/firewall and incident response, and commission an independent penetration test before confidential institutional use. Hosted encryption, direct-origin isolation, MFA, off-site retention, malware-engine operation and recovery readiness require external verification. Reference guidance: OWASP File Upload, Cryptographic Storage and Password Storage Cheat Sheets.

The intended linked Security watch checks the private monitor status every hour and notifies the owner through ChatGPT when at least five authentication/guard/rate rejections (401/403/429) occurred in the previous hour. This signals a review need, not proof of an attack. The existing daily deadline monitor remains separate. Routine status checks are recorded with automated identity. Neither task sends email/SMS or contacts team members externally.
